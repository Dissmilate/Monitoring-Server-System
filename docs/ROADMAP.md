## MVP: агент → метрики → веб-интерфейс в реальном времени

### Этап 0. Каркас
- [x] Соглашения репозитория: `.gitignore`, `.editorconfig`, `global.json`, `Directory.Build.props`, централизованное управление пакетами
- [x] Решение (`.slnx`) с проектами по слоям: Domain, Application, Infrastructure, Api, Gateway, Workers
- [x] Health-check эндпоинты для Api и Gateway
- [x] Архитектурные тесты (правила зависимостей между слоями)
- [x] Smoke-тесты интеграции (WebApplicationFactory)
- [x] CI в GitHub Actions: сборка и тесты
- [x] `docs/architecture.md`

### Этап 1. Хранение данных, аутентификация, реестр серверов
- [x] PostgreSQL/TimescaleDB, EF Core (схема в snake_case), миграции, отдельный Migrator
- [x] ASP.NET Core Identity с cookie-аутентификацией, роли Admin/Viewer, начальный администратор, вход/выход/текущий пользователь, управление пользователями
- [x] CRUD серверов и выдача токенов регистрации (хранится хеш, есть срок действия, повторная выдача отзывает предыдущий токен)
- [x] Ключи Data Protection хранятся в PostgreSQL
- [x] docker-compose: timescaledb, migrator, api (+ документация API в Scalar)
- [x] Тесты: модульные тесты домена и обработчиков; интеграционные тесты на TimescaleDB в Testcontainers (аутентификация, роли, серверы, регистрация)

### Этап 2. Протокол агента и регистрация
- [x] `ServerMonitor.Protocol`: `agent.proto` (`Enroll`, `Ping`)
- [x] Gateway: метод `Enroll`, аутентификация по API-ключу (поиск по префиксу + SHA-256, сравнение за постоянное время), отзыв ключа из веб-интерфейса
- [x] Одноразовость токенов регистрации при параллельных запросах (оптимистическая блокировка по столбцу `version`)
- [x] Агент: Worker Service (systemd / служба Windows), регистрация с повторными попытками, хранение ключа (файл 0600 / DPAPI)
- [x] docker-compose: gateway, демо-агент (профиль `agents`)
- [x] CI: отдельный job на `windows-latest` для агента
- [x] Тесты: API-ключи, правила регистрации, логика агента, хранение ключа на разных ОС, сквозная регистрация (Api + Gateway + агент на TimescaleDB)

### Этап 3. Конвейер метрик
- [x] Сбор метрик агентом: procfs в Linux, cgroup v2 и v1 в контейнерах, P/Invoke в Windows; CPU, память, swap, load average, uptime, диски, сеть
- [x] Ограниченный буфер store-and-forward в SQLite и пакетная отправка с повторными попытками
- [x] Метод `PushMetrics` в Gateway с проверкой данных → Kafka `telemetry.metrics` (идемпотентный продюсер, `acks=all`)
- [x] Запись метрик в TimescaleDB в Workers: гипертаблицы, COPY + `ON CONFLICT`, непрерывные агрегаты, сроки хранения, сжатие; dead-letter топик
- [x] Api: `GET /api/servers/{id}/metrics` с автоматическим выбором разрешения
- [x] docker-compose: kafka (KRaft), workers
- [x] Тесты: парсеры procfs/cgroup и сборщик на тестовых файлах, буфер, отправка, сквозной сценарий агент → Gateway → Kafka → Workers → TimescaleDB → Api

### Этап 4. Канал управления, статус, централизованная конфигурация
- [x] Двунаправленный поток `Connect`: приветствие, сигналы активности, отправка конфигурации, команды и их результаты; новое подключение заменяет старое
- [x] Статус online/offline с атомарными обновлениями, детектор отключения, повторная проверка ключа при сигнале активности, `monitor.events`
- [x] Централизованная конфигурация агента (интервал сбора метрик) с `config_version` и командой `ApplyConfig`, сохраняется на стороне агента
- [x] Outbox `agent_commands`, ретранслятор → `agent.commands` → Gateway доставляет команды подключённым агентам; команда `CollectNow`; истечение срока команд
- [x] Тесты: жизненный цикл команд и сервис подключений на заглушках, конфигурация и обработчик на агенте, сквозные сценарии канала управления (реальный агент, таймауты, отзыв ключа, замена подключения, события)

### Этап 5. Веб-интерфейс
- [x] Blazor WebAssembly + MudBlazor, раздаётся из Api (один origin); вход по cookie и интерфейс с учётом роли
- [x] Список серверов со статусом и основными показателями в реальном времени; страница сервера с живыми графиками (SignalR, поток из Kafka) и историей
- [x] Подключение сервера (одноразовый токен + команды установки), настройки агента, команды, отзыв ключа и удаление; управление пользователями
- [x] Тесты: авторизация в хабе, живые замеры по серверу и события статуса, данные главной страницы, раздача SPA и маршрутизация

### Этап 6. Логи
- [x] Источники на агенте: чтение файлов с учётом ротации и усечения, journald, журнал событий Windows; нормализация уровня; позиции чтения сохраняются в очереди SQLite в одной транзакции с записями
- [x] `PushLogs` с проверкой данных → `telemetry.logs` → индексатор логов → data stream в OpenSearch с удалением по ISM-политике; детерминированные идентификаторы для дедупликации
- [x] Поиск в API (полнотекстовый, по уровням, серверу, периоду, курсор `search_after`) и в интерфейсе (страница логов, вкладка на странице сервера)
- [x] docker-compose: opensearch, генератор тестового лога для демо-агентов
- [x] Тесты: парсеры, чтение файлов (ротация, усечение, незавершённые строки), очередь и отправка, сквозной сценарий агент → Gateway → Kafka → Workers → OpenSearch → Api
- Не сделано: централизованная настройка источников логов (сейчас задаются в конфиге агента), многострочные записи
