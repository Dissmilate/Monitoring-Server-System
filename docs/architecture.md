# Архитектура

ServerMonitor — распределённая система мониторинга серверов. На каждом сервере работает агент, который
отправляет метрики и логи на центральный сервер; сервер сохраняет их, вычисляет оповещения, запускает
через агентов резервное копирование по расписанию и показывает всё в веб-интерфейсе в реальном времени.

> **Состояние.** Реализованы: регистрация и аутентификация агентов, метрики, логи, канал управления
> (статус, конфигурация, команды) и веб-интерфейс. **Оповещения и резервное копирование спроектированы,
> но не реализованы** (этапы 7–8 в [плане работ](ROADMAP.md)); описывающие их части документа помечены
> *(в планах)*.

## Общая схема

```
                 Агент × N   (.NET Worker Service · Linux / Windows)
                 сборщики → пакеты → буфер SQLite → отправка по gRPC
                     │                         │                       ▲
        gRPC unary:  │  двунаправленный поток: │                       │ presigned
        PushMetrics  │  Connect (heartbeat,    │                       │ PUT / GET
        PushLogs     │  конфиг, команды)       │                       │
                     ▼                         ▼                       │
              ┌─────────────────────────────────────────┐       ┌──────┴──────┐
              │ Gateway  gRPC · API-ключи · регистрация │       │ S3 (бэкапы) │
              └─────┬───────────────────────────▲───────┘       └─────────────┘
   telemetry.*,     │                           │ agent.commands
   monitor.events   ▼                           │
              ┌─────────────────────────────────┴───────┐
              │               Kafka (KRaft)             │
              └─────┬─────────▲───────────────────┬─────┘
       telemetry.*  │         │ agent.commands,   │ telemetry.metrics,
                    ▼         │ monitor.events    ▼ monitor.events
         ┌────────────────────┴───┐     ┌─────────────────────────────┐
         │ Workers                │     │ Api                         │
         │ · метрики → Timescale  │     │ · REST (Minimal API)        │◀── HTTPS (cookie) ───  Браузер
         │ · логи → OpenSearch    │     │ · хаб SignalR               │─── WebSocket ───────▶  Blazor WASM
         │ · детектор offline     │     │ · Identity (cookie)         │
         │ · ретранслятор outbox  │     │ · раздаёт Blazor WASM       │
         │ · оповещения (*)       │     │ · live-поток из Kafka       │
         │ · бэкапы (*)           │     │ · поиск логов               │
         └────────────────────────┘     └─────────────────────────────┘

  Общие хранилища:  PostgreSQL + TimescaleDB ← Gateway · Api · Workers
                    OpenSearch               ← Workers (индексация) · Api (поиск)
                    S3 (*)                   ← Gateway (presigned URL) · Workers (очистка) · Api (скачивание)

  (*) в планах, пока не реализовано
```

## Компоненты

| Компонент | Назначение | Основные технологии |
|---|---|---|
| **Агент** | Собирает метрики и логи, буферизует их локально, выполняет команды, применяет централизованную конфигурацию; резервное копирование и восстановление *(в планах)* | Worker Service, systemd / служба Windows, SQLite |
| **Gateway** | Единственная точка входа для агентов: регистрация, аутентификация по API-ключу, приём телеметрии в Kafka, канал управления; presigned URL *(в планах)* | ASP.NET Core gRPC, Confluent.Kafka |
| **Workers** | Потребители Kafka (запись метрик, индексация логов) и периодические задачи: детектор отключения, ретранслятор outbox; вычисление оповещений и планирование бэкапов *(в планах)* | BackgroundService, Npgsql COPY, REST API OpenSearch |
| **Api** | REST API и хаб SignalR для веб-интерфейса, Identity, поиск логов, раздача Blazor WASM, live-поток из Kafka | Minimal API, OpenAPI, SignalR, ASP.NET Core Identity |
| **Dashboard** | Веб-интерфейс | Blazor WebAssembly, MudBlazor, ApexCharts.Blazor |
| **Migrator** | Однократная инициализация: миграции EF Core, гипертаблицы и непрерывные агрегаты, топики Kafka, шаблон индекса и ISM-политика OpenSearch, первый администратор | EF Core |

Gateway, Api и Workers разворачиваются отдельно, но работают с общей базой данных. Это сознательно
**не** микросервисы: это процессы одного приложения, разделённые по характеру нагрузки (агенты,
пользователи, фоновая обработка) и масштабируемые независимо.

## Протоколы

### Агент ↔ Gateway (gRPC, Protobuf)

```proto
service AgentGateway {
  rpc Enroll(EnrollRequest) returns (EnrollResponse);              // одноразовый токен → serverId + apiKey
  rpc PushMetrics(MetricBatch) returns (PushAck);                  // после ack пакет удаляется из буфера агента
  rpc PushLogs(LogBatch) returns (PushAck);
  rpc Connect(stream AgentMessage) returns (stream ServerMessage); // hello/heartbeat/результаты ⇄ конфиг/команды
  // в планах: RequestBackupUpload / RequestBackupDownload (presigned URL для загрузки частями)
}
```

- Телеметрия отправляется отдельными пакетами (unary), а не клиентским потоком: подтверждение на
  каждый пакет даёт простую доставку «как минимум один раз» из буфера агента. Gateway подтверждает
  пакет только после того, как запись подтвердила Kafka (`acks=all`, идемпотентный продюсер).
- Идемпотентность: у каждого пакета есть `batchId` (UUIDv7); метрики пишутся с
  `ON CONFLICT DO NOTHING`, у документов логов детерминированные идентификаторы.
- API-ключ имеет вид `smk_<12 hex>_<секрет>`. Первые 16 символов — несекретный префикс для поиска
  ключа и отображения; сервер хранит только SHA-256 всего ключа (ключи высокоэнтропийные, медленный
  хеш не нужен) и сравнивает хеши за постоянное время.
- Токен регистрации одноразовый даже при параллельных запросах: у агрегата `servers` есть явный токен
  конкурентности `version`, поэтому по одному токену может завершиться только одна регистрация.
  (Не `xmin`: статус переписывает строку при каждом heartbeat, и параллельные правки из интерфейса
  не должны из-за этого падать.)

### Канал управления (`Connect`)

- После регистрации агент открывает поток и отправляет `AgentHello`. Gateway отвечает текущей
  конфигурацией, затем ожидающими командами. Дальше агент шлёт heartbeat (каждые 15 с) и
  `CommandResult` на каждую команду.
- **Статус** (`status`, `last_seen_at`, `connection_id`) обновляется одиночными атомарными запросами
  `UPDATE … RETURNING` с предыдущим статусом:
  - подключение переводит сервер в Online;
  - heartbeat текущего подключения поддерживает Online;
  - закрытие потока переводит в Offline;
  - детектор в Workers переводит в Offline после 45 с без heartbeat (connection id при этом
    сохраняется, поэтому следующий heartbeat «подвисшего», но живого потока вернёт сервер в Online);
  - новое подключение заменяет старое;
  - при heartbeat API-ключ проверяется заново, поэтому отзыв ключа закрывает поток в течение одного
    интервала heartbeat.
- **Команды** — строки в `agent_commands`, которые пишутся в той же транзакции, что и вызвавшее их
  изменение (например, изменение конфигурации ставит в очередь `ApplyConfig`): таблица служит outbox.
  - Ретранслятор в Workers забирает неопубликованные строки с `FOR UPDATE SKIP LOCKED` и публикует
    сигнал в `agent.commands`.
  - Каждый экземпляр Gateway читает все сигналы и доставляет команды подключённым к нему агентам.
  - Подключающийся агент получает всё, что ещё ожидает выполнения. Кроме того, каждое подключение
    перепроверяет очередь при назначении партиций и раз в минуту — на случай потерянного сигнала.
  - Доставка «как минимум один раз» (команда, доставленная в оборвавшееся подключение, будет
    доставлена снова), поэтому обработчики на агенте идемпотентны.
- Изменения статуса публикуются в `monitor.events` для живых обновлений интерфейса.
- В Linux агент хранит ключ в файле с правами `0600` внутри каталога `0700`, в Windows — зашифрованным
  через DPAPI. В docker-compose агент общается с Gateway по HTTP/2 без шифрования; TLS — в бэклоге.

### Kafka (4.0, KRaft)

Сообщения используют те же Protobuf-контракты; schema registry не используется.

| Топик (ключ: `serverId`) | Продюсер → потребители |
|---|---|
| `telemetry.metrics` | Gateway → Workers `metrics-writer`, Api (live-поток, каждый экземпляр) |
| `telemetry.logs` | Gateway → Workers `log-indexer` |
| `agent.commands` | Workers (ретранслятор outbox) → каждый экземпляр Gateway (доставляет своим агентам) |
| `monitor.events` | Gateway, Workers → Api: статус агентов (позже — оповещения, ход бэкапов) |
| `*.dlq` | Сообщения, которые не удалось обработать |

Запись метрик и индексация логов используют общий пакетный потребитель в группах `metrics-writer` и
`log-indexer`: он набирает до 500 сообщений или ждёт 250 мс, сохраняет их, при ошибке хранилища
повторяет запись того же пакета, а сообщения, которые не удалось разобрать, перекладывает в
dead-letter топик. Смещение отмечается (`StoreOffset`) только после сохранения данных и коммитится в
фоне раз в секунду («как минимум один раз»). Синхронный `Commit()` здесь не используется: он может
зависнуть, пока координатор группы недоступен, и остановить весь цикл.

Live-поток в Api и сигналы команд в Gateway нужны каждому экземпляру целиком и только свежие, поэтому
эти потребители не входят в группы: они сами назначают себе все партиции топика и читают с конца.
Так после недоступности Kafka им не нужна перебалансировка группы, они просто переподключаются.

### Веб-интерфейс

- Blazor WebAssembly с MudBlazor и ApexCharts раздаётся из Api, поэтому интерфейс и API находятся на
  одном origin и HttpOnly-cookie аутентификации работает без CORS и без работы с токенами в браузере.
- Текущий пользователь берётся из `/api/auth/me`; любой ответ 401 разлогинивает интерфейс. Элементы
  управления для администратора скрыты от наблюдателей и дополнительно проверяются в API.
- Одно соединение SignalR на вкладку браузера:
  - все клиенты получают изменения статуса и сводку для главной страницы (с ограничением частоты);
  - страница сервера подписывается на замеры этого сервера для живых графиков;
  - клиент переподключается без ограничения числа попыток (например, после сна компьютера), затем
    восстанавливает подписки и перезагружает данные страницы, пропущенные за время отключения.
- Live-поток в Api читает все партиции `telemetry.metrics` и `monitor.events` на каждом экземпляре,
  поэтому каждый экземпляр отправляет данные своим клиентам без SignalR backplane.
- Страница логов в режиме Live раз в 5 секунд запрашивает новые записи с текущими фильтрами и
  добавляет их сверху; окно запроса захватывает 30 секунд назад, чтобы не пропустить записи,
  проиндексированные с задержкой.

### Браузер ↔ Api

- REST по адресам `/api/*`, cookie-аутентификация (`SameSite=Strict`), политики ролей `Admin` и `Viewer`.
- Ключи ASP.NET Core Data Protection (ими шифруется cookie) хранятся в PostgreSQL, поэтому сессии
  переживают перезапуски и работают при нескольких экземплярах Api. В продакшене ключи стоит
  дополнительно шифровать (`ProtectKeysWithCertificate`); в локальном демо они не шифруются.
- Хаб SignalR `/hubs/live` с группами `server:{id}` и `overview`; обновления сводки — не чаще одного
  раза в 5 секунд на сервер.

## Хранение данных

### PostgreSQL (метаданные)

```
servers            id, name, hostname, operating_system, agent_version, status, last_seen_at, connection_id,
                   metrics_interval_seconds, config_version, version, created_at
enrollment_tokens  id, server_id, token_hash, expires_at, used_at
agent_keys         id, server_id, prefix, secret_hash, created_at, revoked_at, last_used_at
agent_commands     id, server_id, type, payload, status, created_at, published_at, delivered_at, completed_at, result
users, roles, …    ASP.NET Core Identity (snake_case)
data_protection_keys

в планах:
backup_plans       id, server_id, name, paths[], excludes[], cron, keep_last, keep_days, enabled
backup_runs        id, plan_id, server_id, trigger, status, started_at, finished_at, size, sha256, object_key, error
restore_runs       id, backup_run_id, mode (NewDir|Overwrite), target_path, status, requested_by
alert_rules        id, server_id NULL (= все серверы), metric, op, threshold, duration, severity, enabled
alert_states       rule_id, server_id, state (Pending|Firing), since, last_value
alerts             id, rule_id, server_id, kind, severity, started_at, resolved_at, ack_by, ack_at, peak_value
```

`agent_commands` служит transactional outbox. Любое изменение конфигурации увеличивает
`config_version` и ставит в очередь команду `ApplyConfig`.

### TimescaleDB (метрики)

```
metrics          (time, server_id, cpu_percent, memory_used_bytes, memory_total_bytes, swap_used_bytes,
                  load_average_1m NULL, uptime_seconds)                          PK (server_id, time)
disk_metrics     (time, server_id, mount, used_bytes, total_bytes)               PK (server_id, mount, time)
network_metrics  (time, server_id, interface, rx_bytes_per_second, tx_bytes_per_second)
                                                                                 PK (server_id, interface, time)
```

- Гипертаблицы (фрагменты по суткам) с непрерывными агрегатами `*_1m` и `*_1h`; оба строятся по
  исходным данным и с агрегацией в реальном времени (`materialized_only = false`).
- Сроки хранения: исходные данные — 7 дней, минутные агрегаты — 30 дней, часовые — 1 год; фрагменты
  исходных данных сжимаются через сутки.
- Разрешение API выбирает по запрошенному периоду: до 3 часов — исходные данные, до 3 суток —
  минутные агрегаты, дальше — часовые.
- Запись: двоичный COPY во временную таблицу в рамках транзакции, затем `INSERT … ON CONFLICT DO NOTHING`
  по первичному ключу, поэтому повторно доставленные замеры игнорируются.
- Скорость дискового ввода-вывода пока не собирается (бэклог): для неё нужны счётчики устройств с
  привязкой к точкам монтирования.

### OpenSearch (логи)

- Data stream `logs-servermonitor` с ISM-политикой: новый индекс раз в сутки, удаление через 14 дней.
- Поля: `@timestamp`, `entry_id` (keyword), `server_id` (keyword), `source` (keyword: путь к файлу,
  юнит journald или `канал/провайдер`), `level` (keyword, нормализованный Trace…Critical), `message` (text).
- Обращение через REST API с помощью `HttpClient`: используемых методов немного, и так нет привязки
  к версии клиентской библиотеки.
- Запись через `_bulk` с операцией `create` и идентификатором `{serverId}:{agentEntryId}`. Повторно
  доставленная запись получает 409 и считается уже сохранённой.
  - Ограничение: идентификаторы уникальны в пределах одного индекса. Дубликат, пришедший после
    суточной смены индекса, сохранится дважды; для этого нужен простой дольше срока хранения в Kafka,
    поэтому это допустимо.
- Поиск: фильтры по периоду, серверу и уровням плюс `match` по сообщению (должны совпасть все слова).
  Результаты сортируются по (`@timestamp`, `entry_id`) по убыванию и загружаются постранично через
  `search_after`. Курсор для клиента непрозрачный (base64url).

### S3 (резервные копии) *(в планах)*

Объекты хранятся как `backups/{serverId}/{planId}/{yyyy}/{MM}/{runId}.tar.gz`; метаданные и SHA-256 —
в `backup_runs`. Presigned URL подписываются для внутреннего (внутри кластера) или внешнего адреса S3
в зависимости от того, где работает агент.

## Устройство агента

- **Метрики.**
  - Linux: `/proc` на хосте. Внутри контейнера агент читает свою cgroup — и v2 (`cpu.stat`,
    `memory.current`), и v1 (`cpuacct.usage`, `memory.usage_in_bytes`; v1 до сих пор использует
    Docker Desktop на WSL 2). Иначе каждый контейнер показывал бы данные всего хоста.
  - Windows: P/Invoke (`GetSystemTimes`, `GlobalMemoryStatusEx`) и `NetworkInterface`.
  - Диски: `DriveInfo` с фильтрацией до локальных постоянных файловых систем.
  - Замеры раз в 10 с попадают в буфер SQLite; отправщик выгружает его пакетами до 500 штук и удаляет
    замеры только после подтверждения от Gateway.
- **Логи.** Каждый источник опрашивается раз в 2 с и возвращает новые записи и следующую позицию
  чтения. Записи и позиция сохраняются в очередь SQLite одной транзакцией, поэтому сбой между ними не
  приводит ни к потере, ни к дублированию строк. Отправщик выгружает очередь пакетами до 500 записей
  и 256 КБ.
  - Файлы (`Agent:Logs:Files`): позиция — смещение в байтах плюс хеш первых байтов файла. Если файл
    стал короче — его усекли; если изменилось начало — его заменили при ротации. В обоих случаях файл
    читается заново с начала. Читаются только завершённые строки. Уровень определяется по ключевым
    словам (`WARN`, `error`, …), время — по метке ISO 8601 в начале строки, если она есть. При первом
    запуске отправляются только последние 64 КБ файла.
  - journald (Linux, определяется автоматически): `journalctl -o json --after-cursor=<cursor>`;
    позиция — курсор журнала, уровень — приоритет syslog.
  - Журнал событий Windows (по умолчанию `Application` и `System`): `EventLogReader` с запросом
    `EventRecordID > n`; позиция — номер записи. Очистка журнала обнаруживается.
  - Идентификатор записи — хеш (путь, смещение, строка), курсор journald или (канал, номер записи),
    поэтому при повторном чтении получаются те же идентификаторы и сервер сохраняет запись один раз.
  - Источники логов настраиваются на агенте, а не централизованно; централизованная настройка — в бэклоге.
  - Ограничения: многострочные записи (стектрейсы) передаются построчно; строки, записанные в файл
    между последним чтением и ротацией, теряются.
- **Резервное копирование** *(в планах)*.
  - tar.gz потоково пишется во временный файл с одновременным подсчётом SHA-256, затем загружается
    частями по presigned URL.
  - Восстановление скачивает архив и проверяет хеш. По умолчанию распаковывает в новый каталог
    `<path>.restore-<timestamp>`.
  - Перезапись исходных файлов требует роли Admin и явного подтверждения.
  - Распаковка защищена от path traversal.
- **Буфер.** SQLite с ограничением размера; при переполнении первыми удаляются самые старые данные,
  потери фиксируются в логе.

## Ключевые решения

1. **Три хоста над общей базой** (Gateway / Api / Workers) вместо модульного монолита или
   микросервисов: у Kafka есть реальная задача, интерфейс для агентов изолирован от пользовательского,
   хосты масштабируются независимо без распределённых транзакций.
2. **Двунаправленный gRPC-поток для команд сервер → агент** вместо опроса: команды и конфигурация
   приходят сразу, а поток заодно служит heartbeat. Источник истины — `agent_commands`; ожидающие
   команды отправляются повторно при переподключении.
3. *(в планах)* **Периодическое вычисление оповещений с семантикой `for:` как в Prometheus** вместо
   потоковой обработки: каждые 15 с вычислитель запрашивает `metrics_1m` и ведёт конечный автомат
   Pending → Firing → Resolved в PostgreSQL. Детерминированно и тестируется с `FakeTimeProvider`;
   единственный активный вычислитель гарантируется advisory lock.
4. **Широкая схема метрик** (столбец на метрику, отдельные таблицы для дисков и сети) вместо узкой
   таблицы имя/значение/метки: набор метрик фиксирован, поэтому типизированные столбцы компактнее и быстрее.
5. *(в планах)* **Планирование резервного копирования на сервере**, а не на агенте: один источник
   истины; запуски, пропущенные из-за отключённого агента, записываются как `Skipped`, а ручные и
   плановые запуски идут по одному пути.

Сознательно не используются:
- **Redis.** Live-поток идёт из Kafka, а heartbeat — это редкие записи в PostgreSQL.
- **MediatR, AutoMapper, MassTransit, FluentAssertions.** Эти библиотеки перешли на коммерческие
  лицензии; хватает обычных обработчиков, ручного маппинга, Confluent.Kafka и Shouldly.
- **Schema registry и .NET Aspire AppHost.** Каждый из них стал бы второй конфигурацией рядом с docker-compose.

## Структура решения

```
ServerMonitor.slnx
src/
  ServerMonitor.Domain/          сущности и правила: серверы, регистрация, ключи агентов, команды (без зависимостей)
  ServerMonitor.Application/     сценарии и порты: IServerRepository, IMetricWriter/Reader, ILogWriter/Reader, ...
  ServerMonitor.Infrastructure/  EF Core/Npgsql, TimescaleDB, OpenSearch, Kafka, Identity
  ServerMonitor.Contracts/       DTO для REST/SignalR, общие с веб-интерфейсом
  ServerMonitor.Protocol/        .proto-контракты: агент ↔ шлюз и сообщения Kafka
  ServerMonitor.Gateway/         хост: gRPC-шлюз для агентов
  ServerMonitor.Api/             хост: REST, SignalR, Identity, раздача веб-интерфейса
  ServerMonitor.Workers/         хост: потребители Kafka и периодические задачи
  ServerMonitor.Migrator/        хост: однократная инициализация
  ServerMonitor.Dashboard/       Blazor WebAssembly
  ServerMonitor.Agent/           Worker Service
tests/
  ServerMonitor.*.Tests          модульные тесты (xUnit v3, Shouldly, FakeTimeProvider, in-memory заглушки)
  ServerMonitor.IntegrationTests Testcontainers (TimescaleDB, Kafka, OpenSearch) + WebApplicationFactory
  ServerMonitor.ArchitectureTests правила зависимостей между слоями
deploy/Dockerfile                один Dockerfile для всех хостов (аргумент сборки PROJECT)
compose.yaml                     весь стек, демо-агент и генератор логов
```

Правило зависимостей: `Domain ← Application ← Infrastructure ← хосты`. Хосты не ссылаются друг на
друга; агент ссылается только на `ServerMonitor.Protocol`.
